# Personal release and recovery

## Manual backups

Open **Menu → Backups and data → Download backup** after important changes and before releases. Save the JSON file in encrypted storage you control and keep a second copy outside the device. The file contains names and private notes in readable form.

Backup version 1 includes the timezone, active and archived people, priority, cadence, meetup dates and notes, and in-app pause, snooze, and dismissal settings. It omits sign-in details, managed Auth records, push subscriptions and delivery state, and the browser's appearance setting. Backup IDs connect people to their meetups. Restoring creates new database IDs, timestamps, and revisions.

For a recovery drill, use two disposable accounts in an isolated environment. Seed one with an archived person, cadence, a backdated meetup with a note, and a paused reminder. Download its backup, sign in to the empty account, choose the file and verify the preview counts and timezone. Apply restore and compare the person, notes and nudge settings. Download again to verify the restored data. Delete both disposable accounts when the drill ends. The automated drill runs in `scripts/tasks.py db-check` using local managed Auth and two newly provisioned accounts.

An existing library blocks restore and stays intact. For an intentional replacement, first download and verify a backup of the current library. Use **Delete all data**, enter your current password, and type **DELETE** before reviewing and applying the replacement file. Deletion clears application records, timezone, device registrations and delivery receipts. It leaves the sign-in account and any previously downloaded copies available. The system-level browser notification permission is managed from the device. Restore accepts files up to 4 MB and uses the file's timezone to validate completed meetup dates. If a valid meetup is dated tomorrow in that timezone after a recent timezone change, retry after the calendar date arrives there.

## Inactive Supabase project and database recovery

For a paused Free project, check its status in Supabase, restore it from the project dashboard, and wait for it to become healthy. Check the exact project reference, runtime connectivity, `/api/ready`, sign-in, and a disposable meetup read/write. Review notification registrations and the scheduler before using external reminders again. Supabase documents a limited dashboard restore window and the backup download procedure for older paused projects. [Supabase project pausing](https://supabase.com/docs/guides/platform/free-project-pausing)

If a project is lost or corrupted, preserve the original and stop its external sender. Recover into a separate project. For owner-data recovery, configure Auth on the replacement project, apply Alembic from the reviewed release, provision a fresh owner account, and use the portable restore above. Reconfigure the exact site/reset URLs and re-enroll each notification device after verifying the restored records. Test the replacement before switching the release configuration.

For database-level backups, use Supabase's documented logical dump procedure for roles, schema and data, with the trusted Session pooler and a pinned CLI. Keep dumps encrypted and separate from application exports. Treat Auth and notification material in dumps as sensitive and verify the restore in a separate project. Recover managed Auth as documented by Supabase and keep Alembic's revision history consistent with the recovered application schema. Free projects need manual backups. [Supabase database backups](https://supabase.com/docs/guides/platform/backups) · [Restore a logical backup](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore)

## Production migration and promotion

1. Keep the synthetic Preview database separate from the owner database. Verify that the protected Preview passes the backup drill, the [phone and VoiceOver review](DEVICE_REVIEW.md), dependency audits, and the monthly review below. Verify the production Auth signup/anonymous controls, allowed recovery destination, actual owner email recovery, and plans before storing personal records. Use [AUTH_SETUP.md](AUTH_SETUP.md) for the Auth checklist.
2. Configure the GitHub `production` environment for protected `main` only, with a required reviewer and the secret `ILP_MIGRATION_DATABASE_URL`. Set its `ILP_PRODUCTION_SUPABASE_REF` variable to the isolated owner project's reference. Use a TLS direct or Session pooler URI with `postgresql+psycopg`. Use a separate runtime configuration in Vercel Production. Keep Vercel's automatic Production promotion disabled so merges cannot skip the migration or staged smoke. [GitHub environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)
3. Keep the current Production deployment ID available for rollback. Confirm a current backup. Dispatch **Production migration** on the reviewed `main` commit after both **Checks** jobs pass on that exact commit. The workflow serializes migrations, verifies the database target, applies Alembic and confirms the resulting head. Alembic also takes a database session lock. The Phase 5 revision is additive and the Phase 4 application can operate while it is installed. Stop the rollout if the migration fails.
4. In a clean staging checkout of the verified commit, replace the Preview Supabase origin in the `connect-src` directive of `vercel.json` with the exact HTTPS origin of the Production Supabase project. Verify this one configuration substitution before deployment. Set the Production public Auth URL/key and server-only database URL in Vercel. Stage with `vercel deploy --prod --skip-domain` from that checkout. Use the authenticated Vercel connection, leave Deployment Protection in place, and verify the staged build targets the correct database.
5. On the staged deployment, check HTTPS/CSP, correct Auth origin, SPA assets, `/api/health`, `/api/ready`, and `no-store` on private endpoints. Run a disposable staged login/create/read/update/delete meetup check and remove the synthetic account before promotion. Promote the verified staged deployment by ID with `vercel promote`. Repeat the smoke on the stable Production origin and verify the exact reset redirect before handoff. Record the commit, CI run, Alembic revision, old/new deployment IDs and smoke outcomes in [IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md). [Vercel staged promotion](https://vercel.com/docs/deployments/promoting-a-deployment)
6. If closed-app reminders are part of the release, provision Production-only Web Push and scheduler secrets, confirm the final origin, and run the [scheduled device checks](PUSH_SETUP.md). Otherwise the app still provides in-app reminders.

## Rollback and incident response

If the app fails after promotion, pause the external sender if enabled. Use Vercel's rollback to the recorded compatible deployment, then rerun health, login and meetup checks. A code rollback leaves the migration applied. The Phase 5 revision adds functions and triggers while preserving earlier tables, routes and RLS. Recover the database separately if a schema or data fault remains. Prefer a reviewed forward migration for a schema defect. For data loss, restore the backup into a separate database, reconcile writes made after that backup, and verify before switching traffic. [Vercel rollback](https://vercel.com/docs/deployments/instant-rollback)
